# HyqSast 结构性漏报盲区（无法优化 / 暂不优化）

> **目的**：记录实测中「当前机制下优化不动、或刻意暂缓」的真实漏报，按项目
> 持续累积，逐步刻画工具的结构性边界 —— 什么洞注定抓不到、什么洞只是还没做。
>
> **适用对象**：对基准 / 真实项目跑完 HyqSast 后，**确认了「规则或图算法改不了」**
> 的漏报。可优化的漏报请走 `docs/漏报面清单.md`（那里是按断点分类的排查清单）。
> 本文档只收录「判了死刑或判了缓刑」的。
>
> **追加方式**：测完新项目，把每条确认漏报按「A–G」归入对应小节的实例表，
> 找不到归属的就新开一类。表格式见每节。最后更新「项目快照」汇总表。
>
> **编号说明**：本文档的 A–G 是「实测漏报分类」，与 `docs/漏报面清单.md` 的
> A–I（漏报断点分类）是**两套独立编号**，不要混读。
>
> **重要提醒**：标「暂不优化」≠ 永远不行。盲区 **F 最初也被判结构性，后来用
> Connexion 提取器 + 路由参数 source 注入补上了**（见 F 节）。判定会随投入过期。

## A. 硬编码凭据 / 弱密钥常量（CWE-798 / 321 / 259）

**判据**：代码里躺着一个常量字符串（SECRET_KEY / 密码 / JWT key），规则引擎
只认「用户输入 → sink」，常量到「危险用法」没有数据流，也没有「字符串字面量
== 凭据」的判定。

**为什么优化不动**：不是漏接，是**压根没建这个漏洞类别**。硬编码凭据本质是
「这个常量看起来像密钥/口令」——需要凭据形状启发式（`secret`/`password`/32
hex 等），召回优先的策略下会喷出海量误报，属于「能做但被刻意搁置」。

## B. 缺失检查型漏洞（IDOR / 越权 / 认证缺失 / CSRF / 限流）（CWE-639 / 306 / 284 / 307 / 352）

**判据**：漏洞不是「污点到达危险调用」，而是**该有的检查没有**——接口能访问
别人资源、没登录就能调、管理员判断只比 username、登录不限制次数、session 不
轮换。

**为什么优化不动**：需要**权限模型 / 认证语义**：谁访问谁、`is_admin` 怎么判、
路由挂没挂 `@login_required`。污点传播在这一类里根本不出场。这是「语义缺口」，
不是「图断链」。

## C. 敏感信息暴露 / 明文存储 / 异常泄漏 / 配置暴露（CWE-200 / 256 / 209 / 522 / 312 / 489 / 215 / 16）

**判据**：漏洞是「把不该给的东西给出去了」——响应里返回 CCN / 密码 / 全量用户、
`str(e)` 把 SQL 报错渲染进页面、明文口令列、debug=True / X-XSS-Protection:0。

**为什么优化不动**：三分支，各有各的断：
- **ORM/序列化层**（`User.serialize`、`jsonify(user)`、column→dict）：分析器不建
  ORM 模型/数据库 schema，字段级别的「哪些列不能出网」无从谈起；
- **异常对象链**（`str(e)` 里夹着注入载荷）：exception 不是变量级数据流，
  `search_term → execute → e → str(e) → render_template_string` 从异常处断；
  同类见 vfa-003（ssti@271，见下），它和 SQLi 同源，只差异常这一跳；
- **配置值**（`debug=True`、header 关防护）：无数据流，纯静态配置判定。

## D. 模板文件侧 XSS —— GT 锚在 .html 模板（CWE-79）

**判据**：同一条反射型 XSS，GT 把位置标在 `*.html` 模板的渲染点（如
`{{ name }}`），我们的 finding 锚在 `.py` 的 `render_template` 调用点。两处对
同一个调用，基准按模板行 +10 内匹配，我们命中 .py 行 → GT 的 .html 侧判漏报。

**为什么优化不动**：要命中模板行，得做「调用点 → 模板文件 → 模板变量」的**模板
语义关联**（`render_template('x.html', name=...)` 解析出 name 在 x.html 里哪个
`{{ }}` 渲染）。这不是断链，是「报告落点与 GT 落点不在一层」。

> 注：flask-xss-002/004 的 .py 侧同款洞已命中（TP），001/003 是同一漏洞的
> .html 锚点侧。

| 项目 | GT | 位置 | 说明 |
|---|---|---|---|
| flask-xss | 001 | templates/sandboxes/unsafe_params.html:6 | request.args 'name' |
| flask-xss | 003 | templates/sandboxes/unsafe_cookies.html:6 | cookie/form 'name' |

## E. 存储型 XSS —— DB 写入 + 模板渲染跨层（CWE-79）

**判据**：`request.form['feedback'] → db 存 → {{ message.message | safe }}` 渲染。
写入和渲染在**不同文件、不同层**，中间隔一个数据库，没有任何变量级连边。

**为什么优化不动**：需要「表单字段 → 数据表列 → 模板变量」的**跨层实体关联**
（ORM 模型 + 模板上下文）。现行 `request.* → render_*` 单函数链覆盖不到存→取
两跳。

## F. 框架路由参数无 source（Connexion / OpenAPI 类）—— **已修复 2026-08-20**

**判据（原）**：Connexion 无装饰器，路由参数只存在于 openapi yaml 的
`parameters`；Python 函数参数在建图期从不被标 source → `get_by_username(username)`
的 username 到不了 sink。当初判「结构性」。

**为什么能修**：框架是**声明式的**（OpenAPI spec 就在仓库里），提取器能确定性
地拿到「handler + 参数名」，再注入到 CPG 图参数节点 —— 不靠语义猜测。

**修复**：`frameworks/connexion.py`（解析 openapi/swagger → 路由）+ `graph.py
mark_params_as_sources`（handler 参数打 source）。**结论：凡路由声明可解析的
框架，参数 source 缺口都可这样补；别再判死刑。**

| 项目 | GT | 位置 | 修复后 |
|---|---|---|---|
| vampi | 001 | models/user_model.py:72 | ✅ TP（SQLi，CWE-89） |

## G. 杂项 —— ReDoS / 枚举 / 弱随机 / 架构级限制（CWE-1333 / 204 / 338 / 770）

**判据**：既无数据流、也无缺失检查，属「没建类别」的边角——正则本身可爆、接口
对响应做差分枚举、`random.randint` 生成令牌、全站无节流。

**为什么优化不动**：要逐类新造判定（正则复杂度分析、枚举识别……），性价比低，
与核心污点主线无关。

## 追加规范（测试新项目时）

1. 扫完新项目，先用 `score.py` 拉出 TP/FN 清单；
2. 对每条 FN，先尝试用 `漏报面清单.md` 的断点分类（能优化 → 去修，记 TODO）；
3. **修不动/暂缓的**才归入本文档：按 A–G 找类，追加一行到对应实例表
   （列：项目 / GT / CWE / 位置 / 一句话根因）；
4. 找不到归属 → 新开 H、I…并说明判据与「为什么优化不动」；
5. 更新顶部「项目快照」表，保持 F2/TP/FN 为最新实测值；
6. 若某类凑满 5+ 条同类实例，考虑转正为独立漏洞类别（写进 `漏报面清单.md`
   或 TODO 路线图）。
