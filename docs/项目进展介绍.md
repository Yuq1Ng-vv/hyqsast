## 一、一句话讲清楚：这是什么

**HyqSast 是一个「自动帮你找代码漏洞」的扫描器。** 你把一个项目的源代码丢给它，
它跑完给你三样东西：

1. **这个项目对外暴露了哪些接口**（HTTP 接口、参数、有没有鉴权）；
2. **哪些地方可能有安全漏洞**（SQL 注入、XSS、越权、反序列化等 20 多类），
   每条都带「漏洞入口 → 传播路径 → 危险函数」的完整链条和代码位置；
3. **一份清单**告诉你哪些接口「没被覆盖到」，需要人去看。

打个比方：**它像一台安检仪，不是判官。** 它不替你做决定，而是把「重点怀疑对象」
一个个标记出来，交给真正的人去复核。它追求的是**尽量不放过坏人**（高召回），
宁可多标几个嫌疑人，也不漏掉真问题。

## 二、为什么做这个（背景与动机）

1. **人工审计太累、太慢**：一个中型项目几千个函数，人眼一行行看不可能看完，
   而且容易看走眼。
2. **商业扫描器（如各大商业 SAST）很贵**，黑盒依赖云平台，代码出去有顾虑。
3. **常见开源工具的两难**：
   - 有的**漏报高**（查不出真问题，形同虚设）；
   - 有的**误报高**（报一堆假问题，把人淹没，最后没人看）。
4. **为什么不用 AI / LLM 直接分析？** 这是本项目一个很明确的取舍：
   - LLM 分析**结果不可复现**——同一份代码这次报 3 个、下次报 5 个；
   - 速度慢、成本高，**没法在 CI（持续集成）里每次提交都跑**；
   - 大模型有时候一本正经地胡说，安全领域不敢赌。
5. **所以我们的答案**：一个**确定性、零 LLM**的扫描器——
   - 同一份代码，**永远得到同一份结果**，可以放进 CI，每次提交自动跑；
   - 依赖极轻（只有 6 个小包），能塞进任何构建流程；
   - 定位清楚：**产出「需要人工复核的候选清单」**，把工程师的时间花在刀刃上。

一句话：**用确定性的静态分析，把人的精力从「大海捞针」变成「对号入座」。**

## 三、它是怎么实现的（给懂技术的人）

### 3.1 整体流程：四步

```
建图 → 提接口 → 跑污点 → 汇总
```

1. **建图**：用 tree-sitter 把源码解析成语法树，再组装成一张「代码属性图（CPG）」。
2. **提接口**：识别 Web 框架的注解/路由，枚举出 HTTP 接口、参数、鉴权信息。
3. **跑污点**：从「污点源」（用户输入入口，如 HTTP 参数）出发，在图上做 BFS，
   找它能不能一路流到「污点汇」（危险函数，如 `executeQuery`）。
4. **汇总**：把命中路径整理成结构化报告。

### 3.2 核心概念

- **污点分析（Taint Analysis）**：安全漏洞的本质大多是「用户输入没被校验/转义，
  直接流进了危险函数」。分析就是追踪这条「污染的流动」：
  `用户输入 → 变量赋值 → 跨函数传参 → 危险调用`。
  找到一条完整的流动路径，就生成一条候选漏洞。
- **代码属性图（CPG）**：把代码表示成一张图——
  - **节点**：函数、参数、赋值、变量引用、调用点；
  - **边**：语法关系、调用关系（谁调谁）、数据流（值怎么流动）、控制流。
  图的好处：**跨函数、跨文件**的传播路径，变成了图上的「找路」问题，
  用图遍历算法就能解，稳定且可解释。
- **规则引擎**：哪些是源、哪些是汇、哪些是净化函数（如 `html.escape`），
  全部写在一个 YAML 规则文件里（`taint_rules.yaml`，约 4600 行）。
  **加一种新漏洞 = 在 YAML 里加几行，不改一行代码。** 这是刻意设计的扩展点。
- **扩展点（给要接新语言/新框架的人）**：
  - 新语言：加一个语言适配器文件 + 注册一行；
  - 新框架：加一个路由提取器文件 + 注册一行；
  - 新漏洞类型：只改规则文件。

### 3.3 工程选型（为什么这么设计）

| 决策 | 理由 |
|---|---|
| 零 LLM、纯算法 | 结果可复现，可在 CI 跑，成本可控 |
| tree-sitter 解析 | 语法级解析，比正则强得多，比编译进语言编译器轻 |
| NetworkX 图遍历 | 复杂传播路径退化成「图上找路」，稳定可解释 |
| 高召回 | 漏报比误报更致命；误报靠「人工复核 + 后续精化」消化 |
| 规则与代码分离 | 不懂代码的安全同学也能加规则 |

### 3.4 本轮重点做的几个「精细化」（P0/P1）

初版能跑通，但为了减少误报、不吞真问题，这一轮做了 6 项：

1. **净化判定修正**（之前的一个真 bug）：旧逻辑只要「某个函数体里出现过一次
   净化调用」，就认为整条传播路径被净化了、直接不报——这会把真漏洞吞掉。
   改成只看「污染确实流经了净化调用」才算净化。
2. **截断可见化**：为了防止大项目输出爆炸，每个漏洞类别默认最多报 50 条。
   以前超出的部分**静默丢弃**；现在明确告诉你「哪类、超了多少条被截断」。
3. **跨函数匹配分级**：一个函数的实参怎么对应到被调函数的形参，旧逻辑是
   「实在配不上就全部连起来」（过近似）。现在按 **参数名→位置→兜底全连接**
   三级匹配，并给边打上置信度标记。
4. **危险参数位置门控**：像 `queryForObject(sql, 用户输入)` 这种，真正的攻击面
   在第一个参数（SQL 语句）；如果污染只流到后面的「参数绑定位」，那不是注入，
   不再误报。
5. **多类别聚合**：同一条路径往往同时命中多个漏洞类别（比如一个表达式既是
   SQL 注入又是代码注入）。以前一条路径报 N 条；现在合并成 1 条主漏洞 +
   `related_categories` 补充说明，报告干净很多。
6. **跨函数返回值追踪**：补上了「被调函数把污染 return 出来、流回调用处」
   这条之前断掉的路。

### 3.5 验证结果（真实项目上的数字）

**OWASP Benchmark**（业界标准的 Java 漏洞基准，2766 个 servlet 测试用例、
11 个漏洞类别，此前在 benchmark 上**四类恒漏报**）：

| 类别 | 脆弱用例 | 检出 | 召回率 |
|---|---|---|---|
| 弱随机数 weakrand | 218 | 218 | **100%** |
| Cookie 未加 Secure | 36 | 36 | **100%** |
| 信任边界 trustbound | 83 | 83 | **100%** |
| 弱哈希 hash | 129 | 89 | 69%（40 个是「算法名写在配置里」，静态不可见） |
| SQL 注入 | 272 | 262 | 96.3% |
| 加密弱点 crypto | 130 | 120 | 92.3% |
| 路径穿越 pathtraver | 133 | 128 | 96.2%（P0 补 FQN sink 规则后 66.2%→96.2%） |
| **全部 11 类合计** | **1415** | **1312** | **92.7%** |

其中 weakrand / hash / securecookie 这类漏洞**根本没有用户输入流进危险 API**
（是「用了不安全的算法/随机数」本身），传统的 source→sink 传播永远够不到、
在基准上恒为漏报 —— 为此新做了一条**非污点流 pattern 检测**：规则命中即报，
再配合「只列精确弱算法、避开强算法子串」的规则设计（详情见 `docs/TODO.md` L 节）。

另一次针对基准的**召回补强（P0，2026-08-21）**：pathtraver 有 40 条漏报源于
FQN（带包名）构造形式没进 sink 规则——`new java.io.FileOutputStream(fileName)`
里匹配不到短名 `new FileOutputStream(`（中间隔了 `java.io.`）。纯追加 5 个全限定
类名模式后，该类别召回 66.2%→**96.2%**、总召回 89.9%→**92.7%**（FN 143→103），
其余类别零丢失。代价是 43 个安全用例新被标记（该类别 FPR 66.7%→98.5%），全部是
流可达性过近似（常量真三元走死分支 / 集合索引不敏感 / 反射返回值过近似），与
trustbound / xss 的 FPR 100% 同类，靠人工复核消化。逐例溯源见 `docs/OWASP漏报清单.md`。

另拿真实开源 Java 项目 **ureport2**（469 个文件、2335 个函数）做回归：

- **召回无损**：改版前后，「入口→危险点」路径 **272 条一条不少**；
- **报告去重**：finding 342 → 272，减掉的 70 条全是重复类别合并，无真漏报；
- 五条基准（vfa / flask-xss / vampi / demo-java + 探针）A/B **全部零丢失**。

   真实的「函数 → 函数 → 函数 → sink」调用链，整理成一份可直接读的报告。

## 五、现场演示（提前跑一遍）

```bash
# 1. 扫描一个 Java 项目，输出完整报告 + 规范版报告
uv run hyqsast /path/to/java/project --language java -o report.json

# 2. 或者用最小示例脚本（也会落盘 report.json / report.canonical.json）
uv run python examples/scan_demo.py /path/to/java/project

# 3. 加自己的规则
uv run hyqsast /path/to/project --rules ./my-rules/ -o report.json
```

**演示项目已备好**：`examples/demo-java/`（1 个文件、5 个接口），刻意含
**4 条真漏洞（跨 3 函数 SQL 注入链 / 命令注入 / 路径穿越 / 已净化 XSS）+
1 个安全样例**，实测 6 条 finding 里有 2 条是已知误报 —— 正好现场讲清楚
「源 → 链 → 汇」三步，顺带把「高召回 → 误报 → LLM 审查层兜底」的叙事带出来：

```bash
# 仓库根目录下直接跑
uv run hyqsast examples/demo-java --language java -o report.json
```

现场念链（规范版报告里现成）：
`GET /users → users → queryUser → execute → executeQuery  ← SINK`（SQL 注入，
一条跨 3 个函数的链，每步带文件和行号）。详细预期结果见
`examples/demo-java/README.md`。

## 六、诚实的边界（汇报时主动说，别等别人问）

这部分一定要讲，主动讲反而加分：

- **高召回的设计，意味着有误报**。产出是「候选清单」，不是最终判定；
  工程上依赖人工复核（这也是我们做规范版报告的原因）。
- **跨函数参数匹配仍是近似**（已分级打置信度，但 BFS 还是会走所有数据流边）。
- **不做**语义级别名解析、反射/动态特性分析；跨函数控制流不展开。
- **语言覆盖**：Java / Python / JavaScript 已支持；Go / PHP 规则已备好但引擎
  适配器还没写（在路线图里）。
- **盲区清单**目前只列「无已知污点源的接口」一类；「未覆盖的危险调用」
  有实现但默认不产出（避免大项目噪声爆炸），可显式开启。

## 八、汇报要点 + 可能被问的问题

### 8.1 你必须说的三句话

1. **「我们做了个确定性、零 LLM 的代码安全扫描器，能在 CI 里跑。」**
   （一句话讲清定位）
2. **「它把工程师从大海捞针变成对号入座：自动圈出所有可疑路径，人只复核。」**
   （一句话讲清价值）
3. **「真实项目上验证过：召回一条不少，误报靠报告分级和人工复核消化。」**
   （一句话讲清可信度）

### 8.2 常用数字（背下来）

- 语言：Java / Python / JavaScript；框架：Spring / Flask / Django / FastAPI / Express
- 漏洞类别：20+ 类
- 规则：内置 ~4600 行 + 外部规则可追加（已适配 5 语言）
- ureport2 回归：469 文件 / 2335 函数，路径 272 条零召回损失，报告 342→272 去重
- OWASP Benchmark：2766 用例全量评分，**总召回 92.7%**（1312/1415；P0 补
  pathtraver FQN sink 规则后 89.9%→92.7%），weakrand / securecookie / trustbound /
  xss / ldapi 五类 100%
- 依赖：6 个轻量包，无 LLM

### 8.3 可能被问的问题（含建议回答）

- **Q：和商业 SAST / CodeQL 官方比，你们强在哪？**
  A：不强在「查得比它们全」，强在**轻、确定性、可复现、能在 CI 低成本跑**，
  定位是兜底扫描 + 候选清单；规则可以从 CodeQL 社区反哺（我们已经在做）。
- **Q：误报这么多，谁来消化？**
  A：靠规范版报告（sink 函数源码 + 真实调用链）把复核成本压到最低；
  后续 P2 的字段级污点、P3 的规则清洗会持续降误报。
- **Q：为什么不用 AI？**
  A：AI 不可复现、不能进 CI、成本高；我们的核心场景是「每次提交自动跑，
  结果稳定」。AI 可以放在「复核」环节做辅助，不放在「扫描」环节做主角。
- **Q：要接入我们自己的项目，要多久？**
  A：Java/Python/JS 直接 `uv run hyqsast <目录>` 就能跑；要加自家框架的路由
  识别或私有漏洞规则，各有对应扩展点，工作量一般以小时计。
- **Q：Go / PHP 什么时候支持？**
  A：规则已备好，缺语言适配器（engine 侧），在路线图 P3，想做时很快。
- **Q：这个评分是客观的吗？**
  A：口径客观——对照 OWASP 官方独立标注的期望结果做确定性比对，用的是官方
  TPR/FPR 口径；而且没往好里刷：误报率 FPR 高达 63.5%，说明确实把可疑的都报了。
  要讲清的一点是 TPR 是「文件级召回」上界（该测试文件里有对应类别的候选就算命中），
  不是每条都精准命中正确位置——精准性由漏报清单逐条溯源 + 人工复核兜底
  （见 `docs/OWASP漏报清单.md` 第 0 节）。
