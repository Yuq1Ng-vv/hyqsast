核心判断：分析器是**确定性、正则/tree-sitter 级、标量变量名级**的污点传播。
漏报的根因几乎都归结为一句话——**污点流经的某一跳不在「变量级 def-use /
同行桥接 / 跨函数边」的建模范围内**。以下是所有已知断点。

## A. 对象/容器内部状态写读 —— ✅ 已修复（同函数容器/Builder）

数据流只认「标量变量赋值 → 使用」。污点**写进对象内部**（容器 / Builder /
数组 / 字段 / setter）再从**另一处读出来**，链必断。

**2026-08 已修复**：`graph.py::_add_container_state_edges` 把 `host.put(k,t)` /
`host.append(t)` / `host.setXxx(t)` 识别为「对宿主内部状态写」，从写调用点连
DATA_FLOW 边到同函数内该宿主的所有 var_ref，读侧复用既有 RHS→LHS /
var_ref→call_site 桥接（漏报面 K 类联动见下）。demo 样例 ⑥（`m.put→m.get`）
与 Builder 形态均实测接住。

**BUF 42 联动收窄**（防误报、不增漏报）：命中 sanitizer 的写调用（如
`ps.setString(1, t)` 是 sql_injection 的 sanitizer）**不再**向宿主传污点 ——
它是安全参数绑定而非状态通道。见 `graph.py::_add_container_state_edges`
顶部注释。

| 形态 | 代码 | 现状 |
|---|---|---|
| 容器 | `m.put("k", t); String s = m.get("k")` | ✅ 修复（demo ⑥ 现报 TP，注释已过时） |
| Builder / 可变累加器 | `sb.append(t); String s = sb.toString()` | ✅ 修复 |
| setter / getter | `o.setX(t); sink(o.getX())` | ✅ 修复（BUF 42 门控 sanitizer） |
| `this.field` | `this.buf = t; sink(this.buf)` | ✅ 修复（同函数 def-use 已含 `this`；跨函数见 J 类） |
| 数组下标 | `a[0] = t; sink(a[0])` | ⚠️ 仍断：def 的 var_name 是 `a[0]`，用是 `a`，配不上 |

## B. 调用图解析盲区（⚙️ 机制确定）

- **同名方法 first-wins**：`callgraph_builder.py:219` 多个文件都有 `execute` 时
  只连**第一个**可达候选（`break # first reachable candidate wins`）。危险实现
  排在第二个 → 污点进安全实现 → 真 sink 接不到。
- **未解析调用点整段断链**：`graph.py:747` 只有 `is_resolved` 的 call_site 才建
  arg→param 边。接收者链 / 泛型 / 静态导入歧义解析失败时，`doThing(t)` 这种
  **表达式语句调用**（无 LHS 可被 RHS→LHS 抢救）污点死在调用点 → 函数内 sink 漏。
- **接口 / 多态分派**：`Base b = getImpl(); b.method(t)` 按声明类型解析，命中
  错的实现或无实现。
- **跨包不可达**：Java 跨包类未 import 且不同目录 → 不解析；Python/JS 相对
  导入、`from x import *` 解析不全。
- **依赖 jar 内部方法**：库包装方法内部调 sink 不可见。部分属预期（无法看到
  依赖内部），但 `Commons` / `HttpClient` 等封装层包装真实危险调用时是实打实
  的漏报。

## C. 返回值追踪盲区 —— ⚠️ 已被行级 RHS→LHS 桥接部分掩盖（已纠正）

**已纠正的旧判断**：早先以为「caller 无 LHS 时返回值接不回」是大断点，但
`graph.py::_add_rhs_to_lhs_edges` 的**行级粗桥接**（同一行内 var_ref →
call_site → 后续赋值全连）把大量看似断链的 return 场景实际接住了 —— 探针
`return x` / `y=x; return y` 均命中。真正的剩余断点收窄为：

- return 追踪只认「标识符 + 赋值中转」（`return x` / `y=x; return y`）。
  `return this.x`、`return arr[0]`、`return sb.toString()` 不追踪（低风险，
  依赖状态桥接/容器桥接兜底的部分场景已通）。
- caller 侧 return 桥接只在**调用行有 assignment** 时生效（`graph.py:853`）：
  调用点在表达式内部 / 无 LHS（`if (isOk(t))`）返回值不接回 caller → 下游
  sink 接不到（⚠️ 推断待实测，优先级低）。

## D. 规则 / 匹配完整性（⚙️ taint_loader.py）—— 最大的实践漏报面

- **未收录的 source/sink API 完全不可见**：子串匹配（`pat in text`），任何不在
  `taint_rules.yaml` / `rules/` 里的调用**连标签都不打**，elements.json 里也没有。
  新框架 / 私有封装 / 新漏洞类都落在这里（`request.newName` 即此）。
- **大小写敏感**：`Request.GetParameter` 之类大小写不符即不命中。
- **sink_excludes 过宽**：正则排除表把真 sink 也排掉 → FN（`graph.py:1162`）。
- 内置 YAML 里 CodeQL 模板噪音（`String(` 等）主要造成误报，但也稀释排查视线。
  BUG 42 已移除 java sql_injection 的 `String(`（实证 FP 元凶）；其余裸类型名
  （`Query(` / `ResultSet(` / `SQLiteStatement(` 等）虽同样偏宽，但存在「靠声明
  点标签兜底」的潜在召回场景，按「解决误报的前提是不增加漏报」铁律保留。
- 缓解：把 `cpg/discovery.py::find_uncovered_sinks` 做成显式开关（P2 已有条目），
  让「规则表没覆盖的危险调用」也可见。

## E. 参数 / 来源标记盲区（⚙️ graph.py::_classify_parameter_source）

- **Spring 隐式绑定**：✅ 已覆盖（实证）。无注解的简单类型参数（`public
  String f(String id)`）分类器不标 source，但 route 层探测（框架提取器对
  `@GetMapping` 等路由 + 参数名的注入）会把它推导成 source —— `probe4`
  实测命中。分类器本身仍是注解/类型驱动（`_PARAM_ANNOTATION_TO_CATEGORY`），
  两条路径取并集，无注解参数不再漏。
- **@ModelAttribute / Body 反序列化对象字段**：整体标 `injection_general`，
  `u.name` 的**字段级**输入依赖 A 类状态写读（断）。
- **source 优先于 sink**：节点同时命中两者只标 source（`graph.py:1150`）——
  若某真实 sink 调用恰好匹配 source 模式，sink 标签被吞。
- **重载签名查表 last-write-wins**：`func_signature_by_name` 按函数名覆盖
  （`graph.py:1101`），重载方法拿错签名 → 注解分类错/漏标。

## F. BFS / 枚举截断（⚙️ analyzer.py::_bfs_to_sink）

- **max_depth=20**：链长 >20 步的 sink 永远够不到。
- **max_paths=5**：前 5 条 src→sink 路径填满即停，第 6+ 条路径独有的 sink 漏。
- **max_findings_per_category=50**：单类别截断（P0-2 有 warning 但只提示不补全）。

## G. 缓存陈旧（⚙️ graph.py::_cache_path_for / _compute_source_fingerprint）

- 指纹只有 `(相对路径, 文件大小)`：改文件但大小不变 → 复用旧图，新增漏洞

## J. 跨函数静态/全局/实例字段状态 —— ✅ 已修复（2026-08-20）

def-use 是函数内的、容器写桥接也只在同函数生效 —— 状态（模块全局 /
static 字段 / `this`/`self` 实例字段）一旦越过函数边界就断链：

- `gbuf = p`（端点 A）→ `exec(gbuf)`（端点 B）
- `queue.add(p)`（A）→ `for x : queue { exec(x) }`（B）
- `this.buf = p`（A）→ `exec(this.buf)`（B）

**修法**（`graph.py::_add_state_bridge` + `collect_state_slots`）：

1. 各语言适配器 `collect_state_slots(tree)` 收拢「越函数边界仍存活」的名字：
   Java 字段声明、Python 模块顶层赋值 / `self.X =`（`_is_state_scope` 排除
   函数内局部变量，避免同名局部变量跨函数串扰）。
2. 建图末期把「状态写」节点连到「状态读」节点：写侧认裸字段赋值 /
   类限定赋值 / `this`/`self` 字段赋值 / 宿主∈slots 的容器写调用；读侧认
   var_ref（函数内有 def 时）+ 按词边界引用状态名的 call_site / assignment
   表达式文本（模块全局/静态字段通常无 def，不生成 var_ref，靠文本兜底）。
3. `this`/`self` 实例状态按类收敛（`func_class` 索引），避免跨类串扰。

验证：静态字段（p2）、静态容器（qw/qr）、模块全局（pystate gw/gr）、
实例字段（this.buf）探针均实测命中。代价是 Python 基准误报上升（见
「已知代价」），但基准 TP 一条不少 —— 满足缺陷平衡铁律。

## K. sink 遮蔽下游真 sink —— ✅ 已修复（2026-08-20）

BFS 旧实现**命中 sink 即终止该路径**（`analyzer.py::_bfs_to_sink` 的
`continue`）—— 若某个**中间节点**被过宽规则误标成 sink（如赋值节点
`String s = foo.build(p)` 命中裸 `.build(`），下游的真 sink（`exec(s)`）
永远探索不到，真实漏洞被一个误报遮蔽成漏报。

**修法**：命中 sink 后**记录路径并继续扩张**（record-and-continue），
不再终止。`if cur in sink_set and cur != src: results.append(...)` 后继续
`for succ in graph.successors(cur)`。

**联动收窄（BUG 42，防误报、不增漏报）**：record-and-continue 会让「路径上
第一个 sink 之后的下游 spurious sink」也暴露，因此同步收窄了三处误报源：

| 收窄 | 内容 |
|---|---|
| 移除裸 `.build(`（java ssrf sink） | `String s = BuilderSvc.build(p)` 不再被标 ssrf，下游真 command_injection 可达 |
| 移除 `String(`（java sql_injection sink） | `new String(bytes)` 不再被标 sql_injection（demo ③ 的 FP 元凶） |
| 容器写跳过 sanitizer 调用 | `ps.setString(1,q)`（sql_injection sanitizer）不再向宿主 `ps` 传污点，`ps.executeQuery()` 不再误报（demo ⑤ 安全样例） |

三条收窄都以「该位置的真实执行 API 另有更精确 pattern 覆盖 / 该调用本身
是安全绑定 API」为前提，基准 TP 零变化 —— 不引入漏报。

## 已知代价（2026-08-20 实测）

状态桥接 + record-and-continue 使 Python 基准误报上升：vfa FP 5→14、
flask-xss 9→19、vampi 20→62；**TP 全部不变（6 / 3 / 1）**。这是 recall-first
的预期成本（产出是「需人工复核的候选」），如需降噪可从「Python 状态槽只收
真正跨函数被写读的名字」方向收窄（见 J 类代价说明）。
