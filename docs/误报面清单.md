# HyqSast 误报面清单（FP surfaces）

> 2026-08 首版。与 `docs/漏报面清单.md` 是姊妹文档，编号独立（本清单 A–E）。
> 目的：把「一条候选为什么会是误报（FP）」的所有可能位置穷举出来，作为
> 降噪优化的靶子。每条标来源：
> **✅ = 实测已修复/已确认**、**⚙️ = 按代码机制核实**、⚠️ = 推断待实测。
>
> 触发背景：用户 **7 万文件 Java 项目**扫出 20442 source / 177727 sink /
> **3,675,408 候选**（sql_injection 183 万），「整个系统都没办法用」。用
> `benchmarks/taint_explosion_probe.py`（05ca579 升级版：sink 模式命中直方图
> + 可达性采样）在 ureport2（200 文件）上做了对照实测，定位出下分各层。

核心判断：误报的根因几乎都归结为一句话——**子串匹配把「看起来像 sink 的
调用」标成了 sink**，再被**过近似桥接**连成可达路径。7 万文件项目候选爆炸
的直接原因是 **sink 打标过宽**（A/B 类，可用模式命中直方图点名），叠加
「规模乘积」性质（C 类），汇总阶段另有独立的 O(findings×全图) 性能 bug（D 类）。

---

## A. sink 打标过宽 · 裸类型名（⚙️ 实测确认主凶之一）

`taint_rules.yaml` 里 java sinks 含一批被压平的 **CodeQL 模板裸类型名**：
`List(` / `Query(` / `ResultSet(` / `SqlRowSet(` / `Cursor(` / `PreparedQuery(` /
`Object(` / `Expression(` / `Html(` / `File(` / `Path(`。打标是**纯子串匹配**
（`taint_loader.py:317` `match_all_sinks` 的 `pat in text`，对 assignment→
`source`、call_site→`expression` 文本匹配，见 `graph.py::_label_taint_nodes`），
因此任何含该子串的节点——类型实例化、强转、构造、方法链——都被标成对应
类别 sink。

**ureport2（200 文件）实测**：

| 模式 @ 类别 | 命中的 sink 节点数 | 性质 |
|---|---|---|
| `Expression(` @ ssti | **215** | 报表表达式引擎 `Expression("…")`，该类 222 个 sink 的 97%，几乎全 FP |
| `List(` @ sql_injection | **68** | 纯噪声 |
| `Object(` @ code_injection | 51 | 任意对象构造/强转 |
| `File(` + `Path(` @ path_traversal | 35 + 31 | 一半是 `new File(`（真 sink），一半是裸类型用法 |
| `Query(` / `ResultSet(` @ sql_injection | 14 + 6 | 裸类型名 |

**先例**：`String(` 已在 **BUG 42** 实证移除（`taint_rules.yaml:3571` 注释）——
`new String(bytes)` 被误标 sql_injection。其余裸类型名当时按「靠声明点标签
兜底」的召回场景保留；本次候选爆炸把代价显式化了。

## B. sink 打标过宽 · 通用方法名（⚙️ 实测确认主凶之一）

java sql_injection / path_traversal / ssrf 等 sink 里混着一批**任何对象上
都可能出现**的通用方法名，同样 `pat in text` 子串命中：

`.execute(` / `.insert(` / `.update(` / `.delete(` / `.query(` / `.select(` /
`.selectOne(` / `.selectList(` / `.getResultList(` / `.getSingleResult(` /
`.batchUpdate(` / `.read(` / `.parse(` / `.connect(` / `.getWriter(` …

**ureport2 实测**：`.execute(` 60 个 sql sink（`executor.execute(task)` /
`command.execute()` 等）、`.insert(` 17、`.parse(` 47 个 xxe sink（
`SimpleDateFormat.parse` / `JSON.parse` / 自定义 parser 全中）、`.read(` 27 个
xxe sink（`bufferedReader.read()` 等）。

**定量结论**：ureport2 的 sql_injection 242 个 sink 里 **~165 个（68%）来自
裸模式**，真 JDBC（`.executeQuery(` + `DriverManager.getConnection(` +
`PreparedStatement(`）只有 ~19 个。7 万文件项目按 ~350× 规模放大，正是
sql_injection 183 万候选的灌入源。

**收窄方向**（须满足「不增漏报」铁律）：裸 `execute(` 收掉后
`Statement.execute(` / `PreparedStatement.execute(` 精确模式仍在；`insert/update/
delete/select` 对 MyBatis 是**真 SQL**（`BaseMapper` 泛型接口方法，无类型可
门控），移除会丢召回——这是 A/B 收窄最难的一档，须先用探针直方图点名哪些
模式在你项目上占比最大，再逐个验证。

## C. 候选爆炸 = 规模乘积，不是单层 bug（⚠️ 探针实测确认性质）

3,675,408 ≈ **20442 source × 177727 sink × 常数可达性**。探针对照实测：

| 项目 | source | sink | sink/文件 | 平均路径/source |
|---|---|---|---|---|
| ureport2（200 文件） | 203 | 732 | 3.7 | **163** |
| 用户 7 万文件 | 20,442 | 177,727 | 2.5 | **~180** |

可达性密度**几乎相同**（163 vs ~180 路径/source）——BFS / 跨函数桥接 /
扇出没有病态膨胀（ureport2 跨文件扇出中位数 1-2、跨函数边只占 DATA_FLOW
4%）。367 万是「sink 数 × source 数 × 同级的可达性常数」在 7 万文件规模下
的**必然结果**。因此：

- **源头不是 bug，是 design 取舍**：追求高召回 + 过近似桥接，在 1-2k 文件
  项目上输出可管理，到 70k 文件必然百万级候选。
- **唯一的乘积项杠杆**是 A/B（sink 数）与 E（可达性常数）；source 数
  （20k 个 `@RequestParam` / `getParameter`）是真实用户输入标记，不可动。
- BFS 枚举本身 20 分钟跑完（用户实测），不是瓶颈；瓶颈是下游处理与
  排查视线被假 sink 淹没。

## D. 汇总阶段 O(findings × 全图节点) —— ✅ 已修复（BUG 62，7207ff9）

汇总（规范版报告）对每条 finding 调 `_sink_function_block`（在**全图**找
sink 函数）+ `_render_chain`（每条**全图扫**重建 callee 表）。7 万文件 ≈
6-20M 节点 × ~1000 findings = **几十亿次节点访问 → 汇总数小时**。用户实扫
「污点传播 20 分钟跑完，汇总跑几小时」，进度条卡 100%（BUG 63）。

**修法**（`analyzer.py`）：
- `_sink_function_block`：全图扫描 → `_file_node_ids` 文件索引（O(本文件)）
- `_render_chain` 的 callee 表：每 finding 重建 → `_callee_at_map` 惰性缓存
  一次（O(全图) 一次，全部 finding 复用），同 key 后写胜出保证字节恒等

pull 后 rerun，汇总应从数小时 → 分钟级。**这是「系统没法用」的第一主因，
已消灭。**

## E. 过近似桥接的可达性放大（⚙️ 机制确定，次要但决定乘积常数）

可达性常数（~180 路径/source）由三层过近似机制抬起来：

1. **跨函数 P1-3 桥接**（`graph.py:1093-1158`）：参数名匹配（high）→ 位置
   匹配（medium）→ **全连接兜底（low，`if not name_matched and not
   positional_done`）**——名称/位置都没对上时过近似的全连。
2. **无条件桥接边**（`graph.py:1160-1170`）：每个实参 var_ref → call_site →
   **全部 callee_fids** → 全部参数。同名方法跨 N 个文件时一条调用连 N 个
   函数体。
3. **Java 可达集放大**（`callgraph_builder.py:470` `same_dir` 同包无条件
   可达；`callgraph_builder.py:299` import 模块名前缀匹配）——同包同名
   方法的 callee_fids 巨大。

规模小时这三层各自贡献的路径少（ureport2 平均每 source 163 条，可管理）；
规模大时它们决定「一个 source 能达多少个 sink」这个乘法因子。**收窄方向**：
桥接边按 callee_fids 扇出分级（扇出大的调用点降置信度/限量）、全连接兜底加
类型/参数个数门控（BUG 56 已做过 setter 兜底删 + 类型门控的精确化先例，
OWASP +10FN 仅 +5FP）。须先跑探针拿 7 万文件项目的扇出直方图与 Top 扇出
点名，再决定。

## 建议优先顺序

1. ~~**D 汇总 O(findings×全图)**~~ ✅ 已修复（BUG 62 = 7207ff9）。用户
   pull 后 rerun 即生效；是「系统没法用」第一主因。
2. **A sink 裸类型名收窄**——铁证项先动（`List(` 纯噪声无召回场景、
   `Object(` / `Html(` 同类），按 BUG 42 移除 `String(` 的先例逐个在
   vfa / flask-xss / vampi / demo-java / ureport2 + OWASP 上验证「原有命中
   一条不少」。
3. **B sink 通用方法名收窄**——先跑探针拿**你项目上**的模式命中直方图，
   点名占比最大的模式；`.execute(` 档（有 `Statement/PreparedStatement.` 精确
   覆盖）先动，MyBatis 档（`.insert/update/delete/select`）最难，须证实
   精确模式或接受保留。
4. **E 桥接可达性收窄**——type-gated / 扇出分级，参考 BUG 56 先例，需
   7 万文件扇出数据支撑。
5. **C 是性质不是 bug**——靠 A/B/E 把乘积项降下来，无独立动作。

## 已知代价

- **收窄 A/B 的前提是「不增漏报」**（缺陷平衡铁律）：每个宽模式移除前须
  确认「该位置的真实执行 API 另有更精确 pattern 覆盖」或「该模式无召回
  场景」（`List(` 即后者）。MyBatis 档若无法精确化则宁可保留过近似。
- 探针采样 / 直方图只读图不改结果，可在扫描机上随时跑（命中缓存）。
