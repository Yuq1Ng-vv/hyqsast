## 0. 一句话结论

规则库整体「广撒网」设计是**有意的**（高召回、输出需人工复核），但存在三类**可以低成本修正、且不牺牲召回**的结构性问题：**(A) 同一条规则被复制到多个类别**（含整表复制）、**(B) 语义方向反了的规则**（sanitizer 当 sink、防御函数当 sink）、**(C) 子串匹配碰上前后缀碰撞**。这三类占了真项目噪声的绝大部分，且与「补漏报」的目标无关——修掉它们不违反缺陷平衡铁律。

## 1. 跨语言系统性机制问题（最优先）

### 1.1 字符串拼接 / 模板字符串当 sink —— 全规则库最大的噪声源

三个语言里都有同一族灾难性 pattern，把**任意字符串拼接**当成漏洞 sink：

| 语言 | sink 类别 | pattern |
|---|---|---|
| python | sql_injection / nosql_injection | `"$SQLSTR" +`、`"$SQLSTR" %`、`"$SQLSTR".format(...)`、`f"$SQLSTR{...}..."` |
| python | ssrf | `"$URLSTR" +`、`f"$URLSTR{...}..."` 等 4 条 |
| python | xss | `"$HTMLSTR" +`、`return ... + "..."`、`return f"...{...}..."` 等 |
| javascript | sql_injection | `"$SQLSTR" + $EXPR`、`` `$SQLSTR${$EXPR}...` ``、`` `...${...}...` ``、`util.format($SQLSTR,...)` |
| javascript | xss | `"..." + $STRING`、`[..., $STRING, ...].join(...)`、`` `...${...}...` `` |
| java | — | （Java 侧未发现此族） |

配合 Python 的 source `f"..."`（**每个 f-string 字面量都是 source**），效果是：**代码里任何一个 f-string、任何一次 `"a" + b`、任何一条模板字符串，只要两端都"恰好"出现，就自洽地产生 finding**。这不是"能导致漏洞"，是规则自指——**几乎不可能真的构成漏洞**，是纯噪声放大器。用户真项目「56 万 log_injection」的构成里，这一族 + `logger.info(` sink 占绝对大头。

### 1.2 防御 / 无害函数被列为 sink（语义方向反了）

- `path.join(`/`path.resolve(`/`path.normalize(`/`path.dirname(`（JS path_traversal）——**拼路径不是读写文件**，path.join 是标准防御式写法。
- `.getCanonicalPath(`/`.getAbsolutePath(`（Java、Python path_traversal）——getCanonicalPath **解析符号链接**，是缓解手段；Python 里 `getCanonicalPath`/`getRealPath` 是 Java 方法（Java 段复制漏网进 Python，Python 根本不存在这两个 API）。
- `url_for(`/`flask.url_for(`/`django.urls.reverse(`（Python open_redirect）——URL **构建器**按视图名反向生成，不受攻击者控制。
- `escape(`（Python xss sink）+ `html.unescape(`（Python xss **sanitizer**）——escape 是 XSS **缓解**函数却被当 sink；`html.unescape(` 把实体**解码**回可执行 `<`（放大器）却被当 sanitizer。**同类别自相矛盾**。
- `defusedxml.ElementTree.*`/`defusedxml.lxml.parse(`（Python xxe sink）——defusedxml 就是**防 XXE 的标准库**，却在内置里被列为 XXE sink（rules/ 的 `defusedxml.` sanitizer 恰好部分抵消，说明两条规则是不同来源叠出来的）。
- `tls.createServer(`/`tls.createSecureContext(`（JS crypto_weakness sink）——创建 TLS 服务器本身不是弱加密。
- `autoescape=False`（Python ssti sink）——这是**配置属性**，不是数据流 sink（污点永远"流"不进 `autoescape=False`）；应走 `pattern_sinks` 机制（如 Java 的 `insecure_hash` 那样），放在 taint sink 位置是死规则。

### 1.3 前后缀碰撞：一条 pattern 吃掉更安全/更长的名字

- Python `ssl.PROTOCOL_TLSv`、`ssl.PROTOCOL_TLSv1`（crypto_weakness sink）→ 子串匹配会命中**安全的** `ssl.PROTOCOL_TLSv1_2`/`TLSv1_3`。目前靠 sanitizer 表里的 `ssl.PROTOCOL_TLSv1_2` 恰好抵消，属于**巧合正确**，一旦 sanitizer 未命中就 FP。同理 `secureProtocol: 'TLSv1`（JS）会命中 `'TLSv1.2'`。
- `Cipher(algorithms.AES(`（Python crypto_weakness sink）——AES 是**强算法**，只有 ECB 模式弱（`modes.ECB` 已单列）。`algorithms.AES(` 单独当 sink = 每次 AES 加密都报弱加密。
- Java `weak_randomness` 里 `Math.random(`（带括号）与 `Math.random`（不带括号）并存：无括号版同时命中 assignment 节点与 call_site 节点 → **同一物理节点出 2 条 finding**（探针实测 1 个 `double r = Math.random();` 报 2 条）。`new Random(` 同理。这是去重缺陷，不是规则缺失。

### 1.4 裸标识符 / 泛方法当 sink（子串匹配爆炸）

| 语言 | sink | 问题 |
|---|---|---|
| javascript | `update` / `insert` / `delete` / `create`（sql_injection） | **裸 SQL 关键词**。`update` 命中任意含 `update` 的调用/属性（`state.update(`、`x.update(`、`Date.update(...)`）；`create` 命中任意 `create(`。规则库最严重的单条 |
| javascript | `del(`（path_traversal） | 命中 Redis `client.del(`、任意 `obj.del(` |
| javascript | `dropb`、`biselect` | **垃圾 token**（疑为关键词截断/OCR 残片），不可能命中真实代码 |
| javascript | `callback(`（xss）、`import(`（ssrf）、`require(...)`（code_injection） | `callback(` 命中任意回调调用；`import(`/`require(` 命中所有动态导入 |
| python | `.run(`（sql_injection） | 命中任意 `.run(`：`app.run(`、`thread.run(`、`pipeline.run(` |
| python | `text(`（sql_injection） | 命中任意 `text(` 调用（`plt.text(`、`Message.text(`…） |
| javascript | `.set(`（deserialization） | 命中任意 `.set(`：Redis `client.set(`、`map.set(`、`cache.set(` |
| python | `.data`（sql source）、`.value`（JS xss source） | 任意 `.data`/`.value` 属性读都变 source |

### 1.5 import 语句当 sink（死规则）

大量条目是 `import`/`require` 文本（污点永远流不进 import 语句，永不产出 finding，只污染 elements 清单）：

- python sql：`import sqlalchemy`、`import pymysql`、`import psycopg2` 等 8 条
- javascript sql：`import 'knex'`、`require('pg')`、`import $S from "$IMPORT"` 等
- javascript ssrf：`@aws-sdk/`、`@google-cloud/`、`@slack/bolt`、`require('puppeteer')` 等 10 余条
- javascript ssti：`import * as $PUG from 'pug'` 等 11 条（squirrelly/dot/nunjucks/mustache/eta/pug/jade/lodash/handlebars/ejs/hogan.js）
- javascript xxe / deserialization / code_injection：`import $XML from '$IMPORT'`、`import * as $SER from '$IMPORT'` 等

死规则不影响 finding 数，但让 `report.elements.json` 的「漏报排查」入口被无关条目淹没。

### 1.6 auth_bypass 类别根本性错位（三语言通病）

auth_bypass 的语义应该是「认证**检查被绕过/跳过**」。但三语言的 sink 表把**认证检查本身**列了进去：

- **认证框架/守卫**：JS `@UseGuards(`、`AuthGuard(`、`JwtAuthGuard(`、`NextAuth(`、`getSession(`、`clerk.`、`supabase.auth.`；Python `Depends(`、`Security(`、`login_required`、`permission_classes`
- **密码/令牌校验函数**：JS `bcrypt.compare(`、`argon2.verify(`、`jwt.verify(`、`jsonwebtoken.verify(`、`jwt.sign(`、`crypto.createHmac(`；Python `bcrypt.checkpw(`、`werkzeug.security.check_password_hash(`、`jwt.decode(`
- **会话/客户端构造**：JS `express-session(`、`createClient(`、`req.headers['x-api-key']`（读请求头是 source 方向）、`req.isAuthenticated(`

这些函数收到污点（比如用户提交的密码、token）是**正常认证路径**，不是绕过。结果：**任何把请求参数传进 `bcrypt.compare`/`jwt.verify` 的代码 → auth_bypass finding**。JS 侧更矛盾的是 `req.isAuthenticated(` 同时出现在 sink 表（auth_bypass）和 sanitizer 表——同一调用既是 sink 又是 sanitizer，自我抵消，行为取决于求值顺序。

> 真实可报的 auth_bypass 形态应聚焦：`jwt.decode(t, verify=False)`（Python 已有 `sink_excludes` 兜 True 侧，但默认 verify 的裸 `jwt.decode(` 仍会 FP）、JWT 密钥硬编码、`is_authenticated` 属性被覆盖、authz 检查缺参数等——这些需要**结构/配置判断**，不是子串 sink 能表达的。

### 1.7 sink_excludes 机制几乎闲置

内置 sink_excludes：python 仅 1 条（`jwt\.decode\(.*verify\s*=\s*True`），javascript **0 条**。而上面列出的几十个「子串碰撞」型 FP（`ssl.PROTOCOL_TLSv`、`subprocess.run(` list 形态、`Model.findAll(` 参数化调用、`setTimeout(fn,...)`）全都**可以用 sink_excludes 正则低成本收窄**，是当前最值得补的机制。

### 1.8 pattern 型类别用错机制

- Java 已正确用 `pattern_sinks` 承载 `trust_boundary`/`secure_cookie`/`insecure_hash`/`weak_crypto`/`weak_randomness`（无 source 流入的 API 滥用）。
- 但 Python 的 `autoescape=False`（ssti）、JS 的 `hardcoded_secret`（`new $F($VALUE,...)`、import jsonwebtoken）仍挂在**污点 sink** 位置。硬编码密钥没有 source 流入（它本身就是常量），作为 taint sink 永不触发；autoescape 同理。应迁移到 pattern 型机制，否则是死规则或误触发。

### 1.9 复制粘贴：同源集散播到多个类别

- **Java：7 组完全相同的 38 条 source 集**（脚本逐条比对确认，`sql_injection` 与 `crypto_weakness`/`info_disclosure`/`format_string`/`header_injection`/`injection_general`/`log_injection` 逐字相同）。后果：一个 `@RequestParam` 同时是全部 7 类 source → 无害 controller 同时产出 format_string/header_injection/log_injection 等不同类别 finding（见 §3.1 探针实证）。
- **Python：`sinks.xpath_injection` 是 `sinks.sql_injection` 的逐字复制**（85 条完全一致）。每条 SQL 查询 → 同时报 sql_injection **和** xpath_injection 两条，xpath 纯属错误归类（真正的 XPath sink `.xpath(`/`XPathEvaluator(` 只在 rules/ 里有）。
- Python xss 的 `sources.xss` 混入 JS 专属 `document.getElementById(`、`.innerHTML`、`response.json(`——Python 代码里不存在这些（JS 段复制漏网）。
- Python path_traversal 的 `.getCanonicalPath(`/`.getRealPath(`——Java 方法混入。

### 1.10 重复报告：同一物理节点多次出 finding

- 弱随机数（Java）：`Math.random`/`new Random` 同时命中 assignment 与 call_site 节点 → 探针实测 1 个无害 controller 里 4 条 weak_randomness（两个调用各 2 条）。
- xxe/ssrf 共用 `xml.etree.ElementTree.parse(`：同一节点标两类，双类别各出一条。
- `f"$SQLSTR{...}..."` 同时是 sql/nosql sink：字符串拼接双类别各报。

## 2. 逐语言速查

### 2.1 Java（sink 25 类 / 683 条，pattern_sinks 机制最成熟）

已在上节列出的：38-source 复制、防御方法当 sink、`.info(`/`.error(` 全日志器 sink、`Class.forName(` 归 sql_injection（应归 code_injection/反射加载）、`.toXML(` 归 deserialization（**方向反了**：deserialization 是 XML→对象；toXML 是对象→XML 序列化）、`org.dom4j` 包名当 xxe sink（命中所有 dom4j 用法）、`String;I)I`/`String;I)I:2,4(` 垃圾（JVM 签名残片当 sql sink）。**探针实证见 §3.1。**

### 2.2 Python（sink 15 类 / 827 条）

除 1.x 列出的：Django/SQLAlchemy **参数化 ORM 方法全量当 sink**（`.filter(`/`.exclude(`/`.where(`/`.annotate(`/`.aggregate(`/`.join(`/`.select_related(`/`.prefetch_related(`/`.values(`/`Q(`/`Model.objects.filter(`）——这些是安全参数化查询，只有 `.order_by(`/`.extra(`/`.raw(`/`RawSQL(`/`.cursor(` 才真可注入。`session.execute(`（SQLAlchemy 参数化）同理。**`json.loads(` 同时是 source（sql 类）和 sanitizer（deserialization 类）**——同一函数身兼两端。`pipes.quote(`/`shlex.split(` 当 code_injection sink（这俩是 shell 转义**缓解**函数）。`torch.save(`/`jsonpickle.dumps(`/`pydantic.parse_obj(`/`marshmallow.Schema.load(`/`ConfigParser.read(` 归 deserialization（序列化/格式解析 ≠ pickle RCE）。

### 2.3 JavaScript（sink 15 类 / 1218 条，规模最大）

除 1.x 列出的：**Node `fs.*` 全量枚举**（约 70 条，含 fd 型 `fs.close(`/`fs.read(`/`fstat(`/`fchown(`——fd 不是用户路径）；`fs-extra.pathExists(`/`ensureDir(` 当 traversal sink（无实际文件内容影响）；Mongoose/MongoDB 的 NoSQL 查询归 sql_injection（`mongoose.Model.find(`、`collection.find(`、`.$gt`/`.$lt`/`.$regex` 操作符）；Sequelize/Mongoose **参数化 ORM 方法当 sink**（`Model.findAll(`/`Model.findOne(`/`Model.findByPk(`）；`util.format(`/`format(` 通用格式化当 sql sink；`WebAssembly.compile(`/`WebAssembly.instantiate(` 当 command_injection（WASM 是沙箱，非命令执行）；`@google-cloud/`/`@aws-sdk/client-`/`azure-` 包名前缀当 cmdi sink；`console.$LOG` 当 format_string sink（所有 console 语句）；`dns.resolve(`/`dns.lookup(` 当 ssrf sink；Next.js `getServerSideProps`/`getInitialProps` 当 ssrf sink（**数据获取函数方向反了**，应是 source）；`setTimeout(`/`setInterval(` 当 code_injection sink（`setTimeout(fn, tainted_delay)` 也命中）。

### 2.4 rules/ 自动加载（CodeQL 适配）—— 真项目噪声的放大器

`rules/python.yaml` 的 `log_injection`（`logger.info(`/`logging.info(` 等 13 条）+ 内置 `f"..."` source = **用户真项目 56 万 log_injection 的直接构成**。`rules/python.yaml` 的 `ssrf`（`requests.get(` 等）与内置 ssrf sink 大量重复。`rules/` 是独立的适配层，**建议先从这里删减，因为它不影响 OWASP Java 基准**，能直接降真项目噪声而不碰内置召回。

## 3. 实证（探针复现）

### 3.1 Java：1 个无害 2 端点 controller → 7 条 finding

探针 `/tmp/rules_probe/C.java`（`@Controller` + `@GetMapping` + `@RequestParam String id`，函数体只做无害操作）：

| # | 类别 | sink | 判读 |
|---|---|---|---|
| 1 | format_string | `String.format("hello %s", id)` | **FP**：字面量格式串 + 参数注入，Java 无此风险 |
| 2 | header_injection | `resp.setHeader("X-Request-Id", id)` | 理论 CRLF 注入，但对跟踪头属常态写法，噪声大 |
| 3 | log_injection | `logger.info("user requested " + id)` | 真 CRLF 风险，但全项目每个日志都报 |
| 4-5 | weak_randomness | `double r = Math.random();`（2 条） | **去重缺陷**：同一节点 2 条 |
| 6-7 | weak_randomness | `Random r2 = new Random();`（2 条） | 同上 |

一个没有任何真实漏洞的 controller 出 7 条。`@RequestParam id` 作为 source 同时点燃 7 个复制出来的 38-source 类别——与 §1.9 吻合。

| 指标 | 数值 |
|---|---|
| OWASP Benchmark TPR（当前基线） | 97.2%（TP 1375 / FN 40） |
| OWASP xss / cmdi / sqli / pathtraver FPR | **100%** / 100% / 99.1% / 100%（safe 用例全被标） |

OWASP FPR 100% 不是偶然——正是 §1 这些「无害响应/参数化查询/认证检查」全被标 FP 的直接证据。

## 4. 优化建议（按性价比排序，均未实施）

1. **删除/收窄字符串拼接型 sink**（§1.1）与 Python `f"..."` source——收益最大，且不碰真实 sink（`.execute(`/`os.system(` 等仍在）。
2. **给碰撞型规则补 sink_excludes**（§1.7）：`ssl.PROTOCOL_TLSv` 前缀、`subprocess.run(` 的 list 形态、`setTimeout(` 的 fn 形态、`Model.findAll(` 等参数化调用。
3. **消除复制粘贴**（§1.9）：删 Python xpath 整表、拆散 Java 7×38 源集、清 Python 里的 Java/JS 残片。
4. **方向修正**（§1.2）：`escape(`/`defusedxml.*`/`getCanonicalPath(`/`path.join(`/`url_for(` 从 sink 移到 sanitizer 或删；`html.unescape(` 从 sanitizer 删。
5. **auth_bypass 类别重构**（§1.6）：只保留真 bypass 形态（`verify=False`、签名跳过、硬编码密钥），删认证检查函数。
6. **死规则清理**（§1.5）：import 型、`String;I)I`、`dropb`/`biselect`、fd 型 fs 函数。
7. **弱随机数去重**（§1.3 尾）：assignment 与 call_site 同源节点合并。

> 每项都符合铁律前提：以上全是「收窄过宽匹配」+「删除死规则」，不切断任何真实 source→sink 路径。落地前按惯例先跑 OWASP 分块回归 + 五基准 A/B，确认 TP 一条不少。

## 5. 附录：审查口径与局限

- 子串匹配引擎的固有边界：`logger.info(` 无法区分「日志内容含 CRLF 可控」与「普通日志」，`subprocess.run(` 无法区分 shell 开/关——这类**机制性局限**只能靠 sink_excludes + pattern 型机制缓解，列在建议里，不当作单条规则错误。
- 本次为静态审查：未全量重跑 OWASP（内存铁律，1.6GB 需分块）；FP 量化以探针 + 已有 OWASP FPR 存档 + 用户真项目计数为准。
- 复核：所有关键 claim 已用脚本在真实 YAML 上逐条核对（dump 曾因 `startswith('java')` 误匹配 `javascript` 产生文本污染，已修正口径）。
