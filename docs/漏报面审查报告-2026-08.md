# 漏报面审查报告（2026-08）

> 全面审查 HyqSast 全量代码（`src/hyqsast/` 全部 22 个模块），目标是**把握项目**、把漏报面（FN）系统化。方法：核心数据流文件深读 + 3 个子代理分片审查外围模块 + 端到端探针实证。每条标注证据级别：🟢=端到端探针实证，🟡=直接读码确认，⚪=子代理读码报告（未复核）。

---

## 一、项目全貌：污点管线的五个层次

HyqSast 的召回能力 = 一条链上每个环节都不掉链子。漏报面的本质是**链条上某一环断掉**。按层分类，便于理解「问题出在哪」：

```
 L0 语法/标签层    taint_rules.yaml 匹配 → source/sink 标签打到 AST 节点
 L1 调用解析层    callgraph.py + callgraph_builder.py → CALLS 边（跨函数可达性）
 L2 数据流层      dataflow.py + graph.py def-use → DATA_FLOW 边（值在函数内流动）
 L3 框架层        frameworks/*.py → 路由提取 + 参数标 source（入口从哪来）
 L4 遍历层        analyzer.py _bfs_to_sink → 从 source 沿边找 sink（可达性拼装）
 L5 休眠层        cfg.py / query.py / coverage.py / discovery.py → 尚未被主链路消费
```

每层的规则独立性：**L0 依赖 taint_rules.yaml**，**L1/L2 依赖 tree-sitter 结构识别**，**L3 依赖框架适配器**，**L4 依赖预算参数**。哪层断，哪类漏报就成片出现。

## 二、高优先级漏报面（当前主链路，成片影响）

### 🟢 H1. JS 全站方法式 sink 全部漏报 —— `languages/javascript.py:319`

**机制**：JS 的 `extract_callee_info` 里 sink 匹配用的完整表达式是 `func_expr.text.decode()`（无括号版本），而 YAML sink 模式是 `xxx.query(` / `xxx.send(` / `eval(` 这种**带括号**的子串。对比 `python.py:338` 用 `full = node.text`（已修，含括号），JS 的没修。

**漏报场景**：整个 JS 项目里 `db.query(sql)`、`res.send(userInput)`、`eval(req.query.cmd)` 全部不命中。我跑了端到端探针（`document.write(q)` + `eval(req.query.cmd)`）→ **0 findings**，sink/source 模式确认都存在。

**修法**：`javascript.py:319` 的 `full` 改成 `node.text`（与 python.py 对齐）。一行修复，召回影响是全 JS 站点的。

---

### 🟢 H2. source 优先于 sink，source 表达式嵌在 sink 调用内时 sink 被吞 —— `graph.py:1534-1541`

**机制**：`_label_taint_nodes` 里「source 优先于 sink」——节点一旦命中 source 就不再评估 sink。当 source 子串（`request.getParameter(`）直接出现在 sink 调用文本（`stmt.executeQuery(...)`）内部时，整个表达式语句节点被标成 source，sink 标签丢失。

**漏报场景**：`String r = String.valueOf(st.executeQuery(request.getParameter("q")));` —— 我跑了端到端探针 → **0 findings**。这是 Java/Spring 里非常常见的「参数直接喂 sink」写法。

**修法**：source 判定后不跳过 sink 评估，而是**分别打标签**（source 和 sink 可以共存于不同子节点）。目前「source 优先」的本意是避免同一节点既当 source 又当 sink，但正确做法是 sink 判定应该在**子表达式**层面而非语句层面。注意：这个修复可能增加 FP（同类节点现在可能同时产 source→sink 链），须按缺陷平衡铁律在基准上回归。

---

### 🟡 H3. JAX-RS 适配器写好了但从未注册 —— `frameworks/__init__.py`

**机制**：`frameworks/jaxrs.py`（304 行，已实现 `@Path`/`@GET` 等注解提取）从未被 `__init__.py` import / `_register()`。注册表只有 flask/django/fastapi/express/spring/connexion。

**漏报场景**：任何 JAX-RS 应用（`@Path("/api")` + `@QueryParam`）零接口提取、零路由参数 source。整个框架零覆盖。

**修法**：`frameworks/__init__.py` 加一行 `_register("jaxrs", JaxrsExtractor)`。纯加法，无 FP 风险。

---

### 🟡 H4. Python/JS 模块顶层调用全丢弃 —— `callgraph.py:210-219`

**机制**：模块顶层语句（非函数体内的调用）caller 为 `None`，在 `build_from_tree` 里被 `continue` 丢弃，无 CALLS 边、无 def-use。

**漏报场景**：脚本式应用（Flask 常见 `app = Flask(__name__)` 顶层初始化 + 顶层 `os.system(user_input)`、Python 一次性脚本 `subprocess.call(cmd)`）的调用全部不可达。

**修法**：给模块顶层建一个合成 caller（`<module>`），或让 BFS 把模块顶层调用当作可达入口。

---

### 🟡 H5. B 类同名函数解析「第一个可达即停」+ 首定义覆盖 —— `callgraph_builder.py:219`、`find_definition:263`

**机制**：跨文件同名函数，`break # first reachable candidate wins`；`find_definition` 返回 `paths[0]`（首定义）。

**漏报场景**：两个 util 模块都有 `process(input)`，调用点可能连到错的实现，另一个实现里的 sink 就漏了。

**修法**：`is_resolved` 之后对同名候选做「全解析」（所有候选都建边），靠 BFS 的 reach 逻辑天然覆盖。这是过近似方向，无 FN 风险，可能有轻微 FP。

## 四、实证证伪 / 修正项（避免假漏报）

这些是深读时怀疑、但**探针证明不是漏报**或有兜底的，写在这里防止未来误报 FN：

| 项 | 结论 |
|---|---|
| **G1** 重载方法签名覆盖（`graph.py:441` 无行号 + `:1476` last-write-wins） | 修正为**精度丢失**：非路由重载方法探针意外出 finding，源头是 def-use 合成参数赋值（code=`@RequestParam String q`）被 taint_rules.yaml 里 16 个类别硬编码的 `@RequestParam` 子串模式兜底命中。recall 靠侥幸，但 path_traversal 等被冲成 injection_general。 |
| **G3** 多行跨函数 arg→param 断链 | 证伪：`_add_varref_to_callsite_edges` 的 [line,end_line] 区间桥接（BUG 46）+ CALLS 边兜住，BFS 无需 arg→param 位置边也能到 callee 内部 sink。 |
| **source 优先于 sink 不是全量 bug** | 常规 `sql = param; st.executeQuery(sql)` 两节点路径正常。只在「source 子串嵌在 sink 文本内」这一种写法断链（即 H2）。 |
