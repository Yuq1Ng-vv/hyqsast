# 性能分析：大项目跑不完（2026-08-22）

> 实测对象：9879 个 java 文件、1,029,783 行（用户提供）。现象：跑了一下午未完成，手动停掉。
> 方法：合成项目分形态复现 + 插桩归因 + 线性外推。结论先行：**建图阶段 O(函数数 × 图规模) 二次方是主凶**，BFS 阶段在纯 source 密集时反而不是瓶颈。

---

## 一、结论摘要

| 形态 | 实测 | 归因 |
|---|---|---|
| 单文件 × 500 方法 | 115.5s | 边构建函数在 `for fn` 循环内全图扫描（O(F³) 单文件内）+ def-use O(F²) |
| 200 文件 × 8 方法（source 密集，近真实形态） | 建图 69.1s / BFS 0.1s | 同一边构建函数 × 累积全图（O(F×G) 多文件） |
| 真实项目 9879 文件 × ~104 行 | 外推建图 ≈ **几十分钟~小时级** | 同上，F≈60k、G≈270 万 → 800 亿次节点迭代 |

**核心根因（一处代码、两种放大）**：`graph.py` 的三个边构建函数
`_add_rhs_to_lhs_edges` / `_add_varref_to_callsite_edges` / `_add_container_state_edges`
**缩进在 `for fn in funcs:` 循环体内**——每处理一个函数就调用一次，每次遍历
**整个 CPG 图**（跨文件累积后是全项目节点）。本应每个文件调用一次。

- 单文件大文件：F 个函数 × 每次全图 → O(F × G) = O(F²)（树节点 ∝ F）
- 多文件项目：每函数 × 到当时的累积全图 → Σ(全图) ≈ O(F × G_final)

两条都是「每函数调用 + 全图扫描」的组合，改一行缩进即消灭 60–80% 耗时。

## 二、实测数据

### 实验 1：单文件 × 500 方法（`/tmp/perfprobe2`，4007 行）

```
add_file 总耗时 = 115.5s
  _add_rhs_to_lhs_edges       × 500 次  44.3s (38%)   ← 每函数一次全图遍历
  _add_varref_to_callsite_edges × 500  45.2s (39%)   ← 同上
  _add_container_state_edges   × 500   0.9s  (1%)    ← 同上（内部较轻）
  build_def_use_chains         × 500   23.8s (21%)   ← 每函数两次全树遍历 O(F²)
  其余（parse/extract/callgraph/label）  <1s
最终图：10500 节点 / 638750 边
```

扩展曲线（def-use 单独，函数数 N）：
```
N= 50 → 0.28s    每函数 6ms
N=100 → 1.06s    每函数 11ms
N=200 → 4.29s    每函数 21ms
N=400 → 17.28s   每函数 43ms     ← 翻倍 ×4，标准二次方
```

### 实验 2：200 文件 × 8 方法（`/tmp/perfprobe4`，29200 行，每方法 4 个 source 参数、1/8 方法有 sink）

```
add_directory 总 = 69.1s
  _add_rhs_to_lhs_edges       × 3200 次  20.0s (29%)   ← 每次扫累积全图
  _add_varref_to_callsite_edges × 3200  18.8s (27%)
  _add_container_state_edges   × 3200    8.4s (12%)
  build_def_use_chains         × 3200    6.2s ( 9%)
  BFS 找 finding                        0.1s          ← source 密集但图链短，BFS 快
最终图：75200 节点 / 367200 边
```

### 实验 3（对照）：200 文件 × 6 方法、无 source 密集（`/tmp/perfprobe3`，12800 行）

```
add_directory 总 = 3.5s   ← 同样每函数调用，但每个函数 1 个 source 参数、图小
```

→ 说明瓶颈随「方法数 × 图规模」放大，不是固定开销。

## 三、真实项目外推（9879 文件 / 1,029,783 行）

- 平均 104 行/文件 ≈ 5–8 方法/文件 → **F ≈ 60k 方法**
- 按 2.6 节点/行（实验 2 实测 75200 节点 / 29200 行）→ **G_final ≈ 270 万图节点**
- 三个边构建函数各做 Σ_每函数(当时全图) ≈ F × avg(G) = **60k × 135 万 ≈ 800 亿次节点迭代**
- Python 单次 dict 迭代 ~50–100ns → **~11–22 小时**。与「跑了一下午」吻合。

> 注：这是**建图阶段**。真实项目跨文件调用多，BFS 会比实验 2 的 0.1s 慢（每 source 沿 CALLS 边跨文件扩散），但建图已是数量级瓶颈，先修建图。

## 四、修复方案（按 ROI）

### P0-1 [✅ 已落地 2026-08-22] 三个边构建函数移出 `for fn` 循环 → 消灭 ~70% 耗时

`graph.py:627/636/643`，12 空格缩进改为 8 空格（方法体级别，每文件一次）：

```python
# 现在（每函数一次 → O(F × 全图)）
for fn in funcs:
    ...
    self._add_rhs_to_lhs_edges(path)
    self._add_varref_to_callsite_edges(path)
    self._add_container_state_edges(path, language)

# 改为（每文件一次）
for fn in funcs:
    ...
self._add_rhs_to_lhs_edges(path)
self._add_varref_to_callsite_edges(path)
self._add_container_state_edges(path, language)
```

语义不变（函数内部已按 `file_path` 过滤，只处理当前文件节点），无 FN/FP 风险。
实验 1：500 方法 115.5s → 预计 <30s（def-use 仍占大头）。

**实测（2026-08-22，纯建图插桩）**：perfprobe2 单文件 500 方法 115.5s →
**17.2s（6.7×）**；perfprobe4 200 文件 source 密集 69.1s → **5.9s（11.7×）**。
剩余耗时大头 `build_def_use_chains`（perfprobe2 中 15.7s / 91%），即下方 P1-3。

### P0-2 [✅ 已落地 2026-08-22] 三个边构建函数内部按文件预索引 → 消灭剩余 O(G) 扫描

即使移出循环，多文件下每文件一次仍扫全图（9879 文件 × 270 万 ≈ 267 亿）。给
`CPGGraphBuilder` 加 `_nodes_by_file: dict[str, list[str]]`（add_file 时按
`file_path` 追加节点 id），三个函数改为只遍历 `_nodes_by_file[file_path]`。
这样总工作量从 O(F×G) 降到 O(总节点数)。

**落地范围**（BUG 50，均以 `_file_node_ids` 收窄，缓存恢复时重建索引）：
三个边构建函数、4.55 参数→赋值桥、`_label_taint_nodes` 两趟扫描。语义逐节点
等价（原本按 `file_path` 过滤全图 → 只遍历该文件节点）。

**回归（铁律）**：OWASP 全量 2740 文件 / 30554 findings 逐条 A/B 对比存档基线
零差异（类别+源+汇位置全同），TOTAL TPR 97.2% / FPR 71.8% 与基线一致；
demo-java 7 findings 一致。存档 `benchmarks/owasp/results/2026-08-22-perf-p01-p02/`。

### P1-3 [待做] `build_def_use_chains` 单趟遍历 / root=body → 消灭 O(F²)

`dataflow.py:66-179` 每函数调 `Traverser(tree).traverse()` 两次（Phase 1 赋值 +
Phase 2 用点），每次都整树遍历再 `_node_in_range` 过滤。F 个函数 = 2F 次全树
遍历。改法：新增按文件批量版「单趟遍历全树、按 enclosing_function 分桶」，或
`traverse(root=body)` 把过滤下沉到遍历器。单文件 500 方法：23.8s → 预计 <2s。
**P0 落地后此为建图唯一剩余二次方**（perfprobe2 中实测 15.7s / 91%）。

### P2 [BFS 预留] source 密集 + 跨文件时 BFS 的保险

实验 2 里 BFS 0.1s 是因为单文件内链短；真实项目跨文件 CALLS 扩散后每 source
可及图大。若修完建图后 BFS 仍慢，再按「反向 BFS 剪枝 / 同源合并 / 并行」处理
（`docs/TODO.md` P3 已有此条）。

**探针复现**：生成器 `perf_gen_probes.py` + 插桩计时 `perf_probe_bench.py`
（仓库根，gitignore），输出 `perf_probes/`。后续性能回归可复用。

## 五、验证计划（缺陷平衡铁律）

性能改动是**纯重构（语义不变）**，但仍按铁律做基准回归：

1. 五基准（vfa / flask-xss / vampi / demo-java / OWASP 200 文件子集）A/B：
   改前 vs 改后 findings 逐条一致（vuln_type + source 位置 + sink 位置）。
2. 探针样例（A/J/K 类 + pattern 型）命中数不变。
3. 500 方法单文件：115.5s → 目标 <30s；source 密集 200 文件：69.1s → 目标 <5s。
4. 真实项目（9879 文件）跑一遍确认从「几小时」→「分钟级」。

> 注意：实验 2 用 `max_findings_per_category=100000` 跑出 findings=0 是正常的
> （该形态 1/8 方法有 sink，但跨函数桥接少）。性能实验只看**耗时**，不看召回。
